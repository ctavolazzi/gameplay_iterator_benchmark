    What we built

    The player

    Local model

    Runs on llama.cpp on this Mac. Each turn it reads the state and picks one option. A grammar forces its answer to be one of the options offered.

    The hands

    Skills

    Code that does the moving: walk to a tree around the pits, gather, craft. The model chooses a skill; the skill acts.

    The record

    Database

    Every decision is saved: what the model saw, its options, its choice, what happened, and how long it took.

    The coach

    Claude

    When a run ends, Claude reads it, scores it, and may rewrite the briefing and the skills. A new playbook is used only after it passes a test.

    The model's weights never change. What changes between runs is the playbook: the advice it reads and the skills it can choose from. Each version is kept, so any run can be matched to the playbook it played with.

    What this does not show

    • It is a toy game on one world. A nine by nine grid, not Minecraft.
    • Most of the skill is Claude's code. The model's job was to follow a five-line list among about six options. Claude's first playbook, v002, offered one option at a time, so the model chose nothing. That was caught by measuring, and the coach now has a rule against it.
    • The Minecraft-trained model was no better here. Andy took 8 decisions to Qwen's 6, twice gathering more wood when crafting the pick was on offer. This says nothing about Andy inside Minecraft, where its training should count.
    • It is not real time yet. The model cannot reuse the unchanged part of a prompt on this llama.cpp build, so it re-reads everything each turn. By the measured speeds, a 200-token prompt and a shorter answer would come to about 2.5 seconds. That has not been tried.
