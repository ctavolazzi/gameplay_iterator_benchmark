Proposal, 2026-10-02

Gameplay Iterator Benchmark

A game-agnostic harness where a local model plays a game on CT's machine, one logged run at a time, and gets measurably better. Claude builds the harness and grades the runs. It does not play. Minecraft is the first game.

Nothing built yet ctavolazzi/gameplay_iterator_benchmark First game: Minecraft Machine: 2015 MacBook Pro, 16 GB

The idea in one line

Same seed, same world, every time. A local model decides what to do. Everything it does is logged, stored, scored, and fed back into its next attempt.

The point is a benchmark that reacts to itself. Run number 40 should beat run number 1 not because a bigger model was swapped in, but because the code around the same small model learned what works in that world.

The harness does not know what Minecraft is. It knows how to reset a world, run an agent for a budget, store and score the result, and feed it forward. Everything Minecraft-specific lives in one adapter, so a second game is a second adapter, not a second harness.

Who does what

The player

Local model

Runs on llama.cpp on this Mac. Reads the bot's view of the world and picks the next action. Starting model: Jan-v3.5-4B, the only chat model already on disk.

The builder and judge

Claude

Writes the runner, the bot, the database and the evaluator. After each run it is called headlessly (claude -p) with the log and a rubric, and returns scores and suggestions. It never steers the bot.

The scribe

Icarus harness

After each run the local model writes the run up, and the daily-note harness (SimpleAgentOS) files it into the Obsidian vault. Documentation is local-model output, not Claude's.

The three goals

Goal 1: the benchmark

One good starting seed, found online and verified in the generated world. A script that plays that world deterministically, logs every step, stores the run in a database, then calls Claude to evaluate the run. The database is what makes two runs comparable.

Goal 2: documentation by the local model

Each run becomes a note in ~/Documents/Personal-Remote-Vault, written by the local model through llama.cpp and filed by the Icarus daily-note harness.

Goal 3: the loop

A runner that fires runs one after another. Each run's evaluation changes what the next run starts with, so play climbs over time. Sequential first; parallel only if it ever earns its place.

How it fits together

The bot never touches the game window. It is a headless client on a local server. CT's installed Minecraft is the spectator seat, not the thing being driven.

One run, start to finish

  1. Reset. Delete the world folder and start the server from the seed. World generation is fully determined by the seed, so the terrain, villages and ores are identical every run.
  2. Load the player. Start llama-server with the pinned model file, temperature 0, and the current version of the skill library and memory.
  3. Join. The Mineflayer bot connects and starts the loop: observe (position, inventory, nearby blocks and entities, health, time of day), ask the model, execute the chosen action, log everything.
  4. Stop at the budget. A fixed number of game ticks and model calls, whichever comes first. Death ends the run early and is recorded as such.
  5. Store. Every step and event goes to SQLite and a raw JSONL file, with the exact inputs (seed, server version, commit, model hash, prompt version) so the run can be reproduced and diffed.
  6. Judge. The runner calls claude -p with the log and the rubric. Scores and concrete suggestions go into the database.
  7. Improve. The local model reads the evaluation and updates its own skill library and memory: which action code worked, what to avoid, what to try first next time.
  8. Document. The local model writes the run note; the Icarus harness files it into the vault's daily note.
  9. Repeat. Next run starts at step 1 with the new skill library.

What "deterministic" means here

Fixed between runsNot fixed, so it is recorded
World seed and server version (terrain, structures, ores)Mob movement and combat, which use the server's own randomness
Code commit, model file hash, prompt version, temperature 0Wall-clock timing: the bot is throttled to game ticks, not real seconds
Action budget and tick budgetThe skill library and memory, which are supposed to change

So: identical inputs give the same world and the same decisions at the same ticks. Where the game itself rolls dice, the roll is logged. A run can always be replayed from its stored inputs and compared step by step.

What "gets better" means

The model's weights do not change. Fine-tuning a model on a 2015 Intel laptop is not realistic, and a benchmark where the model is swapped out is a different benchmark. What evolves is the layer around the model, in the pattern the Voyager paper showed works:

  • Skill library: small, tested action programs (get wood, craft a table, find stone, place a bed) that the model wrote or chose, kept only if they succeeded in a run.
  • Memory: notes about this seed: where the village is, where the cave was, what killed it last time.
  • Curriculum: the next milestone to attempt, chosen from what the last evaluation said was within reach.

Every version of that layer is stored, so any run can be matched to the exact skill library it played with.

How a run is scored

Efficiencymodel calls per milestoneis it learning, or flailing more cheaply
Rubric scoreClaude's evaluationjudgement on decision quality, with written reasons

Automatic metrics come straight from the log and cannot be argued with. The rubric sits on top and explains them.

The database

runs            id, game, started_at, seed, game_version, commit,
                model_hash, prompt_version, skill_library_version,
                budget_ticks, budget_calls, ended_reason
steps           run_id, tick, observation_json, prompt_hash,
                response_json, action, result
events          run_id, tick, kind (item, milestone, damage,
                death, chat), detail_json
metrics         run_id, name, value
evaluations     run_id, evaluator, rubric_version, score,
                reasons_md, suggestions_json
skill_versions  version, parent_version, created_by_run,
                diff_summary

One SQLite file in the repo plus one JSONL per run. Nothing here needs a server. Every run row carries its game, and event kinds and milestone names are defined by the adapter, so Minecraft runs and a future game's runs share one database without sharing a vocabulary.

ProjectWhat it gives usWhat it does not
MineflayerHeadless Minecraft client in Node (4.37.1 needs Node 22, which is installed). Pathfinding via mineflayer-pathfinder.No agent loop, no logging, no scoring
MindcraftA proven set of LLM action primitives on Mineflayer; talks to local models over an OpenAI-style endpoint, which llama-server provides; purpose-tuned Andy-4 models existNo determinism, no database, its own loop we would have to work around

Current call: a thin runner of our own on Mineflayer, borrowing Mindcraft's primitives and Voyager's design, because determinism, logging and the database are the whole point and neither framework provides them. To be re-checked once Mindcraft has been run against the local model.
